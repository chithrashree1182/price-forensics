**Measuring whether Indian e-commerce discounts are real.**

When a listing says *"Was ₹5,000 — Now ₹2,000, 60% OFF"*, two things could be
true. Either the product genuinely sold for ₹5,000 last month, or the price was
raised shortly before the sale so the discount would look larger.

Nobody can tell from the page. The "before" price is unverifiable by design —
it exists only in the retailer's own claim, at the moment they make it.

This project builds the missing evidence: a daily record of what things actually
cost, and an analysis of how often the advertised saving matches the real one.

## The three questions

### 1. Is the "before" price real?

Tracks every listing daily and looks for the signature of a manufactured
discount: a price rise that is held for days, then reversed the moment a sale
begins.

```
₹ ────────────────┐                    ← baseline: the settled, real price
                  └──────────┐         ← the run-up, held ~2 weeks
                             └──────   ← the "sale" price
   |<-- baseline -->|<- rise ->|<- sale ->|
```

The advertised discount is measured from the peak. What a shopper actually saves
is measured from the baseline. **The gap between those two numbers, in
percentage points, is the finding.**

### 2. Do a retailer's MRPs behave like real ones?

MRP is declared by the manufacturer and printed on the pack — it is a property
of the *product*, not the shop. A genuine catalogue therefore shows roughly one
distinct MRP per product, carrying the irregularity of real cost structures.

If a retailer's claimed MRPs instead cluster on a small menu of round numbers,
reused across dozens of unrelated products, those values are not being read off
packaging. They are being chosen — and the one chosen is whichever makes the
discount look largest.

```
$ pf analyse credibility

snapdeal:         38 products share only  9 distinct MRP values
                  diversity 0.24 · top-5 concentration 89% · median discount 79%
                     ₹   999 claimed by 14 different products
                     ₹ 1,499 claimed by 13 different products

reliancedigital:  22 products share    21 distinct MRP values
                  diversity 0.95 · top-5 concentration 27% · median discount  9%
```

**The larger advertised saving sits on the less product-specific set of
reference prices.**

This needs **one day of data** — the argument is about a distribution, not a
time series — which is why it produced the project's first finding.

It cannot show any individual MRP is false, only that a set of them does not
behave the way product-specific prices behave. The output language is
"inconsistent with product-specific pricing", never "fraudulent".

<details>
<summary><b>The approach I tried first, and why it does not work</b></summary>

The original design compared the *same SKU across sellers*: if three retailers
quote three different MRPs for one product, at least two are wrong. That is
implemented and unit-tested in `analysis/mrp_audit.py`, and it never runs.

Nine retailers were evaluated. The obstacle is structural, not incidental:

| Retailer | Result |
|---|---|
| Flipkart | reCAPTCHA challenge, served even for `robots.txt` |
| Croma · Nykaa · Ajio | Akamai HTTP 403 to any non-browser client |
| Vijay Sales · Tata Cliq · Poorvika · JioMart | Catalogue never renders; gated APIs |
| **Snapdeal** ✅ | Scrapes cleanly — unbranded accessories, ₹170–500 |
| **ShopClues** ✅ | Scrapes cleanly — refurbished and feature phones |
| **Reliance Digital** ✅ | Scrapes cleanly — new branded electronics, ₹4k–215k |

**Every retailer selling new branded goods blocks scrapers; every retailer that
permits scraping sells a different class of goods.** No two scrapable sites
share SKUs, so the comparison has nothing to compare — and a tenth retailer
would not change that.

The code stays because the logic is correct and would run given overlapping
catalogues. What is absent is data that cannot be collected. The distribution
test above answers the same question without needing overlap.

</details>

### 3. Is "Only 3 left!" true?

A real stock counter moves. If a listing reports *"only 2 left in stock"* every
day for three weeks while remaining continuously purchasable, the number is
decoration. Measurable directly from the same daily crawl.

## How it works

```
 ┌────────────┐   ┌───────────────┐   ┌──────────────┐   ┌────────────┐
 │  scrapers  │──▶│ normalisation │──▶│    SQLite    │──▶│  Power BI  │
 │  static /  │   │ cross-seller  │   │ star schema  │   │ dashboard  │
 │  browser / │   │  match keys   │   │              │   │            │
 │  wayback   │   └───────────────┘   └───────┬──────┘   └────────────┘
 └─────┬──────┘                               │
       │                                      ▼
       ▼                              ┌───────────────┐
  raw HTML archive                    │   analysis    │
  (gzipped,                           │  inflation /  │
   re-parseable)                      │  MRP / dark   │
                                      │   patterns    │
                                      └───────────────┘
```

**Archive first, parse later.** Every fetched page is stored gzipped before
anything is extracted. Selector bugs surface weeks later, and you cannot
re-scrape the past — but you can re-parse an archive.

**Selectors live in YAML, not code.** E-commerce markup changes every few weeks.
When a scraper breaks, the fix is a one-line edit to
[`config/sites.yaml`](config/sites.yaml), and `pf doctor` reports which
selectors are currently failing.

**Star schema, not a wide table.** A price observation is genuinely a fact with
conformed dimensions (what / where / when). It also happens to be what Power
BI's engine is built for. See [`sql/schema.sql`](sql/schema.sql).

## Is the detector any good?

Two numbers, measuring two different failure modes.

**Precision — are the flags real?** A random, seeded sample of flags is exported
for manual review; the reviewer opens each product's archived snapshots and
price chart and returns a verdict. Precision is reported with a
**Wilson score confidence interval**, because at n≈100 and p≈0.9 the normal
approximation misbehaves.

```bash
pf validate sample --run 3 --n 100    # draw a reproducible random sample
pf validate load reviewed.csv         # write verdicts back
pf validate report --run 3            # precision + 95% CI
```

**Recall — what did it miss?** Unanswerable on real data: you never know what
you failed to flag. So the synthetic generator plants a known number of
inflation events (alongside honest sales as negative controls) and the detector
is scored against that ground truth.

```
$ pf synth evaluate
{
  "n_planted": 11,  "n_detected": 11,
  "true_positives": 11,  "false_negatives": 0,  "false_positives": 0,
  "recall": 1.0,  "precision": 1.0,
  "mean_abs_error_overstatement_pp": 2.0
}
```

**This is a floor, not a ceiling.** The generator plants the exact pattern the
detector looks for, so perfect recovery confirms the implementation matches its
specification — nothing more. Real retail is messier. Manual review of live
flags is what establishes whether the detector actually works, and the synthetic
score should never be quoted as if it were that.

## Rules vs. a learned detector

Three detectors run over the same series, and the comparison is the point:

| Detector | Method | What it's good for |
|---|---|---|
| **Rule-based** | Explicit rise → hold → reverse template | High precision. Blind to anything off-template. |
| **Isolation Forest** | Unsupervised, 18 engineered shape features | Needs no labels. Widens the review queue. |
| **Changepoint** | PELT segmentation (`ruptures`) | Finds regime boundaries itself — no window size supplied |

```
$ pf ml benchmark
detector           flagged   TP   FP   FN   prec  recall     F1
rule_based              11   11    0    0   1.00    1.00   1.00
isolation_forest        12   11    1    0   0.92    1.00   0.96
changepoint             10   10    0    1   1.00    0.91   0.95
rules_AND_if            11   11    0    0   1.00    1.00   1.00
```

**The features are scale-invariant by construction** — ratios and percentages,
never raw rupees. Without that, the model would spend its capacity discovering
that laptops cost more than earphones, which is true and useless.

### The result that actually matters is a negative one

`contamination` tells Isolation Forest what fraction of the data to treat as
anomalous. It does not *discover* that fraction — it obeys it. Sweeping it:

```
$ pf ml sensitivity
 contamination  flagged   prec  recall     F1
          0.05        3   1.00    0.27   0.43
          0.15        8   0.88    0.64   0.74
          0.25       12   0.92    1.00   0.96   <- true rate is 0.22
          0.40       20   0.55    1.00   0.71
          0.50       24   0.46    1.00   0.63
```

**F1 swings from 0.43 to 0.96 purely on a hyperparameter you cannot know on live
data.** The peak sits almost exactly at the true anomaly rate — which the model
was told, not given a chance to find.

Two things follow, and both are deliberate:

1. **Isolation Forest does not detect manufactured discounts.** It detects
   *unusual series*. Those sets overlap but are not the same — its false
   positives are genuinely volatile products, not bugs. That is what
   unsupervised anomaly detection means.
2. **The rule-based detector stays the primary instrument**, and the learned one
   widens the review queue. `rules_AND_if` is the highest-confidence set and is
   what any headline claim should be built on.

## Thresholds were fixed before the data

Every detection parameter lives in
[`config/targets.yaml`](config/targets.yaml) and was committed **before**
collection began — checkable in `git log`.

This matters. A detector tuned after seeing results can produce any headline you
want. Pre-registering the thresholds is what separates a measurement from a
story.

```yaml
detection:
  inflation:
    lookback_days: 21
    min_rise_pct: 10.0
    min_hold_days: 3       # excludes one-day glitches
    min_observations: 10
```

## Two implementations, deliberately

Inflation detection exists twice: in Python
([`analysis/inflation.py`](src/priceforensics/analysis/inflation.py)) and in SQL
([`sql/03_inflation_candidates.sql`](sql/03_inflation_candidates.sql)).

Written from the same specification with different mechanics — Python walks the
series and tiers confidence; SQL uses framed window functions. When they
disagree, one of them has a bug. It is the cheapest cross-check available, and
it means the Power BI model can recompute candidates on refresh without a Python
round-trip.

## Collection ethics

This studies retailer behaviour; it is not a load test. Full policy in
[`docs/ethics.md`](docs/ethics.md).

- `robots.txt` is checked and honoured before every request
- 4–6 second delays with jitter; exponential backoff on 429/503
- Category listing pages preferred — one request returns ~40 products, which is
  both faster and far lighter on the retailer than 40 product pages
- Public listing pages only. No accounts, no logins, no checkout, no personal data
- Images and fonts blocked in the browser scraper (~80% less bandwidth)

### What live testing changed

`pf doctor` was run before any collection began, and it rewrote the design:

1. **Two of the three target sites were unusable.** Flipkart serves a reCAPTCHA
   page (even for `robots.txt`); Croma returns Akamai 403 to non-browser
   clients. Both were dropped rather than evaded — see [ethics](docs/ethics.md).
2. **Prices were not in the HTML.** Reliance Digital hydrates its grid
   client-side, so CSS selectors found nothing.
3. **The first fix passed every check while being completely wrong.** Reading
   `window.__INITIAL_STATE__` returned data — the *same twelve iPhones* for
   every category, including air conditioners. It was static SEO boilerplate.
   `health_check` now asserts that categories return *different* products,
   because "returns data" and "returns correct data" are not the same claim.

The working design reads schema.org **JSON-LD** — an `ItemList` on category
pages for discovery, a `Product` block per item for price. That contract is
published for Google's benefit, so breaking it costs the retailer search
traffic, which makes it far more stable than any CSS class name.

4. **GitHub-hosted runners cannot collect — proven by run #1.** The retailers'
   CDN returns HTTP 403 to datacenter IPs, *including for `robots.txt`
   itself*, and Python's robotparser fails closed on a 403: unreadable robots
   means "disallow everything". The scraper therefore made exactly zero
   requests from the runner — the politeness layer refusing to crawl where it
   cannot confirm permission, which is correct behaviour. Collection runs from
   a residential connection via launchd (`scripts/daily_collect.sh`), where
   `robots.txt` is served normally and permits these paths; GitHub Actions
   runs the test suite instead.
